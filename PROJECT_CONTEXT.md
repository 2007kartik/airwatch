# AirWatch — Project Context & Implementation Specification

## 1. Project Overview
**Project name:** AirWatch — Real-Time Air Quality Monitoring Dashboard Using IoT and Analytics.

Build a working web application that demonstrates continuous environmental monitoring using simulated sensor data. No physical sensors or Wokwi simulation are used in this version. A standalone Python script generates sensor-like readings every 5 seconds.

**Important:** This is a software-based prototype using simulated data, not a real-world air-quality measurement system. Never describe generated values as actual measurements. Simulated PM2.5/PM10 values are illustrative only and are not measured by hardware.

## 2. Chosen Technology Stack
- Frontend: React
- Styling: Tailwind CSS
- Charts: Recharts
- Frontend API client: Axios
- Backend/API: FastAPI (Python)
- Database: PostgreSQL
- ORM: SQLAlchemy
- Database migrations: Alembic
- Validation: Pydantic
- ASGI server: Uvicorn
- Data generator: standalone Python process, one reading every 5 seconds
- Local development: PostgreSQL through Docker Compose is recommended
- Version control: Git
- Development environment: Antigravity, with frontend and backend in one workspace

**Do not use Wokwi or require physical sensors.** Keep the architecture ready for real sensors to replace the simulator in a future version.

Kafka is optional and excluded from the initial implementation. First complete and test the end-to-end app without Kafka. Add it later only if explicitly requested.

## 3. End-to-End Architecture
Python Sensor Simulator (every 5 seconds)
→ `POST /api/readings` to FastAPI
→ FastAPI validates the payload and applies rule-based processing
→ PostgreSQL stores sensor readings and alerts
→ React polls FastAPI every 5 seconds
→ Dashboard updates KPI cards, charts, and alert history

The simulator must run independently of the React browser tab. Prefer a standalone Python process, not a simulator tied to FastAPI startup, so API restarts and browser sessions do not control data generation.

## 4. Sensor Data Model
Use clear field names and UTC timestamps. Suggested fields:
- `timestamp`: UTC timestamp
- `temperature_c`: simulated temperature in Celsius
- `humidity_percent`: simulated relative humidity percentage
- `gas_raw_value`: optional simulated raw gas-sensor-like value
- `pm25_ug_m3`: optional simulated PM2.5-like value
- `pm10_ug_m3`: optional simulated PM10-like value
- `source`: `simulated` for all records generated by this prototype

Include PM2.5/PM10 only if needed for the dashboard. If included, label them as simulated. Do not imply that an MQ-series gas sensor measures PM2.5 or PM10. Do not claim official AQI unless a valid, documented calculation using appropriate pollutant inputs is implemented. Prefer “simulated pollution indicator” over “official AQI.”

Generate plausible values that change gradually, with occasional configurable spikes. Avoid completely independent random values that make charts jump erratically. Make the interval configurable, defaulting to 5 seconds.

## 5. Proposed PostgreSQL Schema
Create at least these tables using SQLAlchemy models and Alembic migrations.

### `sensor_readings`
- `id`: primary key
- `timestamp`: timezone-aware timestamp
- `temperature_c`: numeric/float
- `humidity_percent`: numeric/float
- `gas_raw_value`: nullable numeric/float
- `pm25_ug_m3`: nullable numeric/float, simulated only
- `pm10_ug_m3`: nullable numeric/float, simulated only
- `source`: string, default `simulated`
- `created_at`: timestamp

Add indexes for timestamp and commonly filtered fields as appropriate.

### `alerts`
- `id`: primary key
- `reading_id`: foreign key to `sensor_readings.id`
- `alert_type`: string
- `severity`: `warning` or `critical`
- `message`: text
- `observed_value`: nullable numeric/float
- `threshold_value`: nullable numeric/float
- `status`: `active` or `acknowledged`
- `created_at`: timezone-aware timestamp
- `acknowledged_at`: nullable timezone-aware timestamp

Avoid duplicate alerts for the same reading and rule. Put configurable thresholds in a central configuration module or environment variables, not scattered throughout the code.

## 6. Backend Responsibilities and Endpoints
Use a modular FastAPI structure. The backend should:
1. Validate incoming records using Pydantic.
2. Save valid readings to PostgreSQL.
3. Apply configurable rule-based thresholds.
4. Create alert records when thresholds are crossed.
5. Provide endpoints for latest readings, history, analytics, and alerts.
6. Return clear HTTP status codes and error messages.
7. Use UTC timestamps consistently.
8. Configure CORS for the local React development URL through environment configuration.
9. Read secrets and connection strings from `.env`; commit only `.env.example`.
10. Include health/status endpoints and useful logging.

Suggested endpoints:
- `GET /api/health` — API and database health
- `POST /api/readings` — ingest one simulator reading
- `GET /api/readings/latest` — latest reading
- `GET /api/readings?limit=...&start=...&end=...` — history with pagination and optional time filters
- `GET /api/analytics/summary` — current values and summary statistics
- `GET /api/analytics/trends?range=...` — chart series for selected period
- `GET /api/alerts?status=...&limit=...` — alert history
- `PATCH /api/alerts/{alert_id}` — acknowledge an alert

Use consistent response schemas. Do not return unlimited history by default.

## 7. Simulator Requirements
Create a standalone Python script/process that:
1. Generates one record every 5 seconds by default.
2. Produces gradual changes rather than totally random jumps.
3. Can occasionally create configurable spikes to demonstrate alerts.
4. Adds an ISO 8601 UTC timestamp.
5. Sets `source` to `simulated`.
6. Sends each record to `POST /api/readings`.
7. Handles temporary API/network failures with retry/backoff and logs failures.
8. Supports configuration for API base URL and interval.
9. Does not depend on React being open.
10. Has clear start/stop instructions.

Prevent accidental multiple simulator loops. Document how to run one simulator process.

## 8. Analytics and Alert Rules
Start with transparent, configurable, rule-based analytics rather than machine learning.
- Validate numeric values and configured bounds.
- Handle missing/invalid data safely.
- Calculate averages, minimums, maximums, changes over time, and counts over a selected period.
- Support configurable thresholds for selected simulated indicators.
- Create alerts with the triggering reading, observed value, threshold, severity, and message.
- Distinguish collected/simulated values from derived indicators.
- Label thresholds as demo/configurable thresholds, not regulatory health advice.
- Do not fabricate a validated AQI value. If an AQI-like visualization is included, label it illustrative/simulated and explain its limitations. Prefer not to include official AQI in the first version.

## 9. React Dashboard Requirements
Build a polished, responsive dashboard using React, Tailwind CSS, Axios, and Recharts. Include:
1. **Overview/KPI cards:** latest temperature, humidity, simulated pollution indicator(s), active alert count, last update time.
2. **Live readings:** latest record and connection/status indicator.
3. **Historical trends:** line charts for selected readings, with readable axes, tooltips, legends, and a time-range selector.
4. **Alerts panel:** severity, message, timestamp, status, and acknowledge action.
5. **Analytics summary:** average/minimum/maximum and threshold-violation count for selected period.
6. **Data source label:** visible “SIMULATED DATA” indicator across the dashboard.
7. **System status:** API/database connectivity and last successful update based on real health checks.

Use clear loading, empty, and error states. Poll the backend every 5 seconds using a managed interval cleaned up on component unmount. Avoid overlapping requests and handle API errors gracefully. Do not hardcode historical data as if it came from the database.

## 10. Visual Direction
Use a modern, professional environmental analytics style suitable for a college project:
- Clean layout and consistent spacing
- Deep navy/charcoal text with teal/cyan accents
- Light neutral background; optional dark mode only if implemented consistently
- KPI cards, readable charts, subtle borders, restrained shadows
- Responsive desktop/mobile layout
- Accessible contrast and legible font sizes
- No excessive gradients, clutter, or meaningless animations
- Charts and cards must be connected to API data
- Clearly disclose simulated data

Use Docker Compose for local PostgreSQL if convenient. Document exact commands to:

2. Create/activate Python virtual environment and install dependencies.

4. Start FastAPI with Uvicorn.
5. Start the Python simulator as a separate process.

## 13. Testing and Acceptance Criteria
The project is complete only when:
- PostgreSQL starts and backend connects.
- A valid POST creates a sensor reading in the database.
- Invalid records are safely rejected.
- Simulator sends a record approximately every 5 seconds.
- Database accumulates readings over time.
- Dashboard reads data from backend/database, not hardcoded mock objects.
- KPI cards update as new records arrive.
- Trend charts show persisted historical readings.
- Configured threshold crossings create alert records.
- Alerts panel displays database-backed alerts.
- Acknowledging an alert persists its status.
- Refreshing browser does not erase data.
- API/database failures are shown clearly.
- Dashboard visibly labels generated data as simulated.
- README setup instructions are complete.

Add focused tests for schemas, threshold logic, endpoints, and simulator payloads where practical.
